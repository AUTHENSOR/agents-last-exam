# Run or upgrade to ALE v1.1

ALE v1.1 selects **122 active tasks** after 30 retirements. Use matching task
code, environment profiles, images and data together. The website has the
[configuration reference](https://agents-last-exam.org/docs?p=pages/configure.html)
and [run tutorial](https://agents-last-exam.org/docs?p=pages/run.html).

Task designs and source are frozen. Use the matching images and data pinned in
the [asset manifest](../../releases/v1.1/assets.json). The
[task review](v1.1-task-review.md) records validation scope and limits; it does
not certify complete agent validation of the release.

To run the original requirements instead, follow the [v1 guide](v1.md).
Use v1 code, legacy images and fresh logs, not v1.1 assets or results.

## What changes from v1

**56 active tasks require reruns; 66 remain eligible for retention.** The six
open-source conversions below are included.

| Change | Tasks | What counts |
| --- | ---: | --- |
| Instruction | 46 | Agent-facing prompts and instructions, including input documents |
| Verification | 43 | Scoring logic, acceptance rules and grader execution |
| Environment | 31 | Task-specific software, dependencies, setup, staging, paths, resources or platform |
| Data | 23 | Input materials, starter/helper assets, models, media or reference answers |

Counts overlap: a task can appear in several rows. Classification follows the
content of a change, not which repository stores it; a prompt edit inside a
data archive counts as Instruction. The [per-task map](../../releases/v1.1/upgrade.json)
records each category. Retired tasks, unselected variants, inactive metadata,
packaging-only cleanup and shared framework changes are excluded from these counts.

The [task review](v1.1-task-review.md) records each modified task's decision,
source/data disposition and validation type. Instruction-only schemas/examples,
grader-only changes and runtime-only scripts do not separately count as Data.

The changes follow three principles:

- Preserve the original business goal and intended difficulty; changing software
  must not remove required work.
- Make grading match the public requirements, accept valid equivalent answers,
  and correct unsupported thresholds or incorrect reference answers.
- Supply necessary inputs and working runtimes without giving away the solution;
  keep hidden references separate from the agent's workspace.

Six formerly licensed tasks keep their IDs and business goals while moving to
open-source Linux workflows:

| Task | v1.1 workflow | Supported environment |
| --- | --- | --- |
| `engineering/2d_drawings_to_3d_building_model` | Blender building reconstruction | Docker or Linux VM |
| `engineering/cailian_road_highway_alignment_2` | FreeCAD Road alignment | Linux VM |
| `engineering/gcode` | FreeCAD CAM, LinuxCNC and CAMotics machining | Linux VM |
| `engineering/inner_support_elevation_optimization` | Kratos excavation and support analysis | Linux VM |
| `visual_media/music_transcription` | MuseScore notation, PDF and MIDI | Docker or Linux VM |
| `visual_media/project_migration` | Ardour project, mix and stems | Docker or Linux VM |

All six use the Linux VM image with QEMU or Google Cloud. The default Docker
profile supports the three workflows listed above. Runtime compatibility checks
cover native save/reopen, export and task artifacts; see the task review for
their scope and limits.
G-code's replay requires process/network isolation unavailable in that profile.
Road requires systemd process supervision; inner-support also requires writable
delegated cgroups for its worker resource limits. Use a Linux VM for these three;
installing the applications alone does not provide those OS facilities.

`engineering/mold-flow` is removed: its full four-cavity fill/pack/cool/demold
workflow has no validated open-source replacement at the original scope.

`education_info/homework_grading_numerical_pdes_instance_02` is retired because
feedback verification was overly tied to fixed wording. A further 28 tasks are
retired from v1.1; the [task review](v1.1-task-review.md#retired-tasks) lists all
30. Retirement is a release-scope decision, not a claim that every retired task
is defective.

Published data and images are unchanged. Standalone data packages **150 tasks**,
including 28 now inactive; VM images package **151**, including 29 inactive
(the same 28 plus PDE). Inactive payloads have no active source implementation
or selection-list entry and do not increase the 122-task benchmark.

## Run v1.1

From the v1.1 checkout:

```bash
uv sync --all-packages
cp -n secret/.env.example secret/.env
cp example_exp.yaml my_experiment.yaml
```

Fill in the agent and provider credentials in `secret/.env`. Follow the
[Google Cloud setup](../quickstart.md), [QEMU setup](../local-qemu.md), or
[Docker setup](https://agents-last-exam.org/docs?p=pages/local-docker.html),
then choose the environment and task list in `my_experiment.yaml`:

| Task list | Tasks | Environment |
| --- | ---: | --- |
| `selected_tasks/full.txt` | 122 | `configs/environments/environment_gcloud.yaml` |
| `selected_tasks/cpu.txt` | 117 | `configs/environments/qemu.yaml` |
| `selected_tasks/ale_cli.txt` | 86 | Linux VM profile; includes desktop workflows |
| `selected_tasks/docker_support.txt` | 78 | `configs/environments/docker.yaml` |

Difficulty lists under `selected_tasks/full/` contain 45 near-term, 46
full-spectrum, and 36 last-exam tasks; they overlap. Docker excludes eight
Linux tasks requiring nested runtimes, namespaces, or systemd/cgroups; use QEMU
for those tasks. AWS and Alibaba Cloud CPU profiles require matching v1.1
images; their existing images are not verified for the six converted workflows.

Start with `tasks: selected_tasks/hello_both.txt` on a VM provider, then switch
to the desired benchmark list. Set `wall_time_s: 18000` for a five-hour agent
budget, and size `concurrency` for your available resources.

```bash
uv run python -m ale_run run my_experiment.yaml --dry-run
uv run python -m ale_run run my_experiment.yaml
```

Environment profiles default to `output_path: null`: bulk task output stays in
the sandbox; run metadata, trajectories, evaluations, and telemetry are still
collected under `output.root`. Use `cleanup_mode: keep` to inspect deliverables
there. Retained VMs consume memory; stop or delete them after preserving needed
evidence. With `cleanup_mode: delete`, sandbox files are removed at cleanup.

## Keep versions together

The [asset manifest](../../releases/v1.1/assets.json) records dataset revisions,
disk checksums, cloud image identities, and the Docker digest.

| Component | Pin to preserve |
| --- | --- |
| QEMU guest disks | `qemu.image_revision` in each snapshot of `configs/environments/qemu.yaml` |
| Google Cloud images | Copy the named `images.*.gcloud` images; optional `gcloud.image_revision` verifies the numeric `sourceImageId` of your project's copy, which gets a new ID |
| Docker runtime | The profile selects `docker.pinned_image` from the manifest; optional `docker.image_revision` verifies a SHA256 image ID or repository digest |
| Task data | `huggingface.*.revision` and `task_data.archive_sha256` in the manifest |

In custom QEMU profiles, rename `hf_revision` to `image_revision`, keeping the
same pin. Image revision settings are nested in each snapshot's provider block.
`run.json`'s `environment.image_revision` records the acquired identity even
without a configured pin. For QEMU remote disks, it records the resolved HF
commit or GCS generation; the requested HF pin remains in source metadata.

QEMU and Google Cloud images contain task data. Keep QEMU disks and overlays
on persistent storage, with capacity for downloads and retained guests. Check
the actual filesystem and available RAM before allocating. Remove
`image_revision` when changing a QEMU disk source from Hugging Face to GCS or
a local file.

Docker needs the separate data archive. Obtain approved access to the
[archive dataset](https://huggingface.co/datasets/agents-last-exam/agents-last-exam-data-archive),
authenticate, then run from the repository root on persistent storage:

```bash
IMAGE=$(jq -r '.docker.pinned_image' releases/v1.1/assets.json)
docker pull "$IMAGE"
REVISION=$(jq -r '.huggingface.archive.revision' releases/v1.1/assets.json)
SHA256=$(jq -r '.task_data.archive_sha256' releases/v1.1/assets.json)
scripts/fetch_task_data.sh --revision "$REVISION" --sha256 "$SHA256"
```

The fetcher verifies the archive and installs into an absent or empty
`task-data-v1.1`; do not merge it with an old data directory. The Docker profile
uses `task_data_source: local:task-data-v1.1`. Only the current task's inputs and
software are staged before the agent; references are staged afterward.
Direct `hf://` task-data staging is not implemented. Guest-side GCS staging
uses `task_data_source: gs://ale-data-public/v1.1` and evaluator credentials.

## Upgrade existing logs

`run.json` records `task.revision` before setup: a deterministic SHA256 of task
folder file names, contents, executable bits, and link targets, ignoring runtime
caches.
Resume skips completed or timeout units only with a matching hash; missing or
mismatched hashes rerun. `environment.image_revision` records provider image
provenance. Keep image and dataset pins alongside the task code.

Known limitation: the excavation-support and UV-reproduction evaluators leave
local review files under their task folders, which changes the folder hash.
After those evaluations finish, move
`tasks/engineering/inner_support_elevation_optimization/scripts/evidence/task-source-reviews/`
and `tasks/visual_media/uv_reproduction/.tmp_soft_eval/` outside the checkout
before resuming. Preserve any evidence you need; these generated files are not
part of the frozen task source.

The upgrade scope retains 66 tasks, reruns the 56 updated tasks, and removes
the 30 retired tasks. Stop the experiment before applying the upgrade.
The helper previews by default. Applying removes
changed or retired task logs and stamps retained, unmodified legacy logs with
the current revision. Back up logs you want to preserve first, then resume
with the same experiment name and `output.root`:

```bash
uv run python scripts/upgrade_v1_logs.py LOG_ROOT
uv run python scripts/upgrade_v1_logs.py LOG_ROOT --apply
uv run python -m ale_run run my_experiment.yaml
```

For an older or custom v1 baseline, add `--from-commit COMMIT` to the helper.
To reproduce v1 instead, follow the [v1 run guide](v1.md) with original code,
legacy images and fresh logs. Do not reuse v1.1 logs for v1.
