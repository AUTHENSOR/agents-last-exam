HF Sandboxes

Run the supported Ubuntu subset as one fresh Hugging Face Job per run unit. The orchestrator, local authentication proxy and local executors still run on your host. No local Docker daemon is needed for the task container.

Supported Linux subset
Start with the CPU Linux task list from the local Docker provider. Container compatibility does not establish HF compatibility. This provider has not passed v1.1 acceptance on HF infrastructure.

What runs where

The hfsandbox provider starts one HF Job per run unit from agentslastexam/ale-ubuntu22-docker, then talks to it over the job's exposed port. The orchestrator process itself needs only an HF token and outbound HTTPS — it can run on a laptop, a CI runner, or another HF Job.

Host requirements

  • An HF token with the jobs scope (hf auth login, or HF_TOKEN in the environment).
  • Approved access to the gated task-data dataset on Hugging Face.
  • A private HF bucket to hold the extracted task-data archive.
  • A persistent-disk host for data preparation, a running Python orchestrator, and a local authentication proxy per active job.
  • A separate, inference-only HF_INFERENCE_TOKEN for the example agent. Never pass the Jobs or bucket token to the solver.
  • A Hugging Face account authorized to run paid Jobs, with sufficient credits, hardware quota, and private-bucket access.
hf auth whoami
uv sync --all-packages

Fetch task data once

The image ships without task inputs or references. Request access to the ALE task-data archive, then: 

hf buckets create <namespace>/<bucket> --private
hf buckets sync <encrypted-reference-tree> hf://buckets/<namespace>/<bucket>

Prepare the tree on verified disk-backed storage, not host /tmp or another tmpfs. It must contain <domain>/<task>/<variant>/{input,software,reference.7z}. Encrypt reference archives and their headers before uploading. Keep ALE_REFERENCE_ARCHIVE_PASSWORD only on the orchestrator until evaluation. Do not mount the plaintext archive extraction tree: every agent can read every mounted file, even on a read-only bucket. Startup rejects plaintext reference directories and symlinks across configured mounts, including references for other tasks.

Use the shipped environment

Point volumes at that bucket in configs/environments/hfsandbox.yaml: 

volumes:
  - hf://buckets/<namespace>/<bucket>:/mnt/ale-task-data:ro
task_data_source: mounted:/mnt/ale-task-data

then run the premade example, which wires configs/agents/qwen_code_hf.yaml (Qwen3.5-9B via the HF router) to this environment for demo/tool_smoke only: 

uv run python -m ale_run run example_hfsandbox_exp.yaml

Screenshot tasks need an image-capable model and route. GLM-5.3 Chat rejected image content in the 2026-10-15 preflight; do not use that text-only route for visual tasks. The Qwen example route was not validated by the Pi runs below. Check endpoint image support and availability before allocating a Job.

On 2026-10-15 Pi with text-only GLM-5.3 via Z.ai completed demo/readfile_secret unassisted with score 1.0 through the real HF provider, executor, task setup/evaluation and cleanup, using a temporary 4.02 GB desktop image, not the release image. Actual native read/write calls and the generated output were independently checked. Mounted hello also scored 1.0, but required operator display recovery and browser cleanup. The official image timed out during its cold pull without reaching RUNNING. These results do not establish official-image or unassisted GUI acceptance; the shipped environment still selects the official release image.

For data-less tasks only (demo/tool_smoke and demo/seecheck, plus setup-generated demo/readfile_secret) you can drop volumes and use task_data_source: baked_in_sandbox instead. The image must still contain an empty input/ directory at <task_data_root>/demo/<task>/base/input. Tasks without reference data need no reference.7z.

Resource sizing

Set flavor to any value hf jobs hardware lists. Before allocating, the provider checks the live flavor CPU/RAM against the task card and ephemeral capacity against min_storage_gb (default 200 GB). Some tasks require 16 vCPU and approximately 60 GB RAM, so one fixed 8-vCPU flavor cannot cover the whole list. Verify ephemeral storage can hold the unpacked image and task working data; compressed image size is not sufficient. Do not assume 50 GB is enough for the release image. The v1.1 manifest contains 37.39 GB of compressed layers. It includes all layers of the previously verified 88.29 GB unpacked image, so its unpacked layer sum is at least that large, before pull overhead or task scratch space. The live hardware API on 2026-10-15 reported only 50 GB for both cpu-basic and cpu-upgrade. The preset uses cpu-xl (16 vCPU, 124 GB RAM, 1000 GB ephemeral storage), the least expensive CPU-only flavor meeting the 200 GB floor in that API response. Recheck hardware and prices before running. Override min_storage_gb only after verifying the alternative image's unpacked size, pull overhead and task scratch requirement. The example starts at concurrency 1. Cold pulls count toward start_timeout; job_timeout caps Jobs. idle_timeout applies only to the optional Sandbox transport, not Jobs.

Output options

The example uses output_path: null to avoid bulk collection. Run metadata and trajectories are still recorded. Choosing output_path: local copies produced files through the exposed port. See Choose where task output goes for other destinations.

Current limits

  • Linux tasks only, same subset as the local Docker provider.
  • The sandbox shares the job container's kernel and is not VM-isolated.
  • transport: sandbox requires a Hub build that actually exports Sandbox. The inspected installed Hub 1.20.1 does not. Prefer transport: job; a generic 1.x version requirement is not sufficient.
  • Rootless-Docker exclusions, GPU, Windows, nested runtimes, systemd and cgroup-dependent tasks are not covered by this profile.
  • cleanup_mode: keep leaves the remote resource billable but closes the local proxy. Retain its owner/job ID for manual inspection and cancellation.
